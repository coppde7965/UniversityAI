## 本版相對 v0 草案的主要變更

1. **每條需求給予穩定編號**（`FR-xxx-nn` / `NFR-xxx-nn`），供 BDD feature 檔以 tag 追溯，見 §9。
2. **每條需求補上驗收條件**，草案中「系統可以⋯」的敘述無法驗收，一律改寫為可判定真偽的條件。
3. **新增 §5 資料模型**。草案反覆提及「結構化資料」卻未定義；該 schema 是課程建立、行事曆、更新比對、問答四項功能共同依賴的介面，屬於需求而非實作細節。
4. **新增 §2.2 決策紀錄**，把架構前提寫成明示決策，並標註推翻後受影響的需求。
5. **新增需求來源分類**，區分「設定既有系統」與「自行開發」（分類本身於 v1.2 隨架構調整，見 §2.3）。
6. **補上草案遺漏的需求**：學生查詢範圍限制（`FR-CHT-03`）、課綱輸入格式限制（`FR-SYL-01`）、AI 產出的來源與信心標註（`FR-SYL-03`）。
7. **新增 §1.6 名詞定義**，統一 BDD 場景用語。

## v1.4 變更

本版有一項**推翻既有決策**的查證結果，以及一項修補 SRS 內在矛盾的調整，兩者都會改變架構文件的寫法。

- **`D-05` 改寫：AI 呼叫分為兩條路徑。** 查閱 Moodle 5.2 原始碼後確認，AI 子系統的動作模型**無法承載結構化輸出**——`generate_text` 的建構子只接受一個提示字串，而 `\core_ai\manager` 在三處把動作命名空間寫死為 `core_ai\aiactions\`，外掛無法定義可經標準介面設定的自訂動作。因此生成類功能（摘要、差異說明、問答）走子系統，結構化抽取（`FR-SYL-02`）走外掛自訂介面。`NFR-EXT-03` 隨之改寫，把「換供應商零改動」的承諾按路徑分開陳述，並要求通用實作作為退路必須隨第一版交付。
- **新增 `D-10`：課綱於既有課程內上傳。** 舊版「由課綱建立課程」與 §1.4 的權限定義互相矛盾——課程不存在時老師沒有課程層級角色，`FR-SYL-01` 要求的課程檔案區也不存在。改為課程外殼先建立、系統負責填入內容。連帶改寫 `FR-SYL-01`、`FR-CRS-01`、`FR-CRS-02` 與 `DM-SYLLABUS.course_ref`。
- **新增 `D-09`：目標版本釘為 Moodle 5.2。** 附版本支援時程表。同時載明 **Moodle 自 5.1 起把網站根目錄移入 `public/`**，三個外掛的安裝路徑與容器掛載路徑皆須照此。
- **`FR-CAL-02` 與 `FR-CAL-03` 依「行事曆只支援 Google」的決定改寫。** Google Calendar 的訂閱由 Google 伺服器端抓取，本機站台不可達，故 `FR-CAL-02` 的驗收改為直接驗證系統產出的 iCal 內容；Google 的展示路徑改由 `FR-CAL-03` 的 API 推送承擔，並由「目標」升為「必要」、擴及學生。
- **`NFR-SEC-06` 展開為可驗收的規則**：白名單、黑名單、去識別化規則與四條驗收條件，並要求與 `OI-03` 測試集去識別化共用同一份實作。
- **`DM-OPSTATUS` 的 `workflow` 欄位更名為 `operation`**，並調整其值以反映 `D-10`。
- **§8.4 第一‧五階段新增三項驗收條件**，作為撰寫架構文件前的實作閘門。

## v1.3 變更

四項環境與架構約定入案：

- **`D-04` 擴充為「一切執行環境皆以 Docker 提供」**：PHP、Composer、測試工具、Behat 瀏覽器與 Python 評測鏈全部容器化，主機端只需 Docker 與 GNU Make。掛載位置改置於專案目錄下以利換機展示，**但資料庫資料目錄是例外**——理由與替代做法（`make db-dump`）見該決策。
- **新增 `D-08`：分層採 MVVM，以 Moodle Output API 既有機制實現**，不自建框架。同時載明伺服器端沒有資料繫結、只有 `block_universityai` 前端具備繫結性質，避免文件與口試說明失準。
- **§2.5 擴充**：容器組成與掛載配置表、`.gitignore` 與隱私注意事項、Makefile 目標清單。其中 Behat 需要 `selenium` 容器與獨立 dataroot 兩點，是常在第一次跑測試才發現的坑，已預先寫明。
- **新增 `NFR-MNT-05`（環境可重現與可攜）與 `NFR-MNT-06`（分層邊界）**，讓上述兩項決策有可驗收的條件而不只是宣示。

## v1.2 變更

新增 `D-07`：系統改以 **Moodle 外掛套組**交付，並以能上架 Moodle 外掛目錄為結構前提。這是目前為止影響最大的一次調整，因為外掛執行於 Moodle 行程內，可直接呼叫內部 API，不受對外 Web Service 介面的限制。

**連帶消除三項外部依賴**：`local_wsmanagesections`（章節寫入改用內部 API）、`tool_trigger`（事件改用外掛自己的觀察者）、以及 **n8n**（排程、非同步與重試改用 Moodle Task API）。原本評估中風險排序第三的「拿不拿得到可安裝外掛的站台」與第二的「聊天助理的身分傳遞」都因此大幅降低——後者從跨服務簽發憑證，簡化為 Moodle 既有的權限檢查，`FR-CHT-03` 也從「目標」升為「必要」。

**其他調整**：

- §2.3 需求來源分類改為「組態／平台／自建」三類，原「外掛」「整合」兩類取消，受影響的八條需求已重新標記。
- 新增 `NFR-SEC-05`（金鑰保管，取代原 n8n 加密金鑰）、`NFR-SEC-07`（Privacy API）、`NFR-MNT-04`（符合上架規範）。`NFR-SEC-01` 由 Web Service token 最小權限改為 Moodle 能力檢查一致性。
- `NFR-EXT-03` 強化為「站台管理員可不改程式碼切換供應商」，這是 `OI-06` 得以延後的前提。
- 新增 §2.5 開發工具約定：產品程式碼為 PHP，Python 保留於不隨外掛發行的評測工具鏈，相依改以 uv 管理。
- §9 追溯規則改用 Behat（Moodle 內建），原 pytest-bdd 的 feature 檔隨 `OI-05` 移除。
- `OI-03`、`OI-07` 依建議結案；`OI-06` 確認延後至 MVP 之後。

## v1.1 變更

原 `OI-01`、`OI-02`、`OI-04`、`OI-05` 四項待決事項已由團隊決定，結果併入 §2.2 成為 `D-04`（修訂）、`D-05`、`D-06`，並在 §10.1 留下結案紀錄。連帶調整：

- 本機部署使雲端行事曆無法抓取訂閱網址、Moodle 亦無對外寄信管道，`FR-CAL-02` 與 `FR-NTF-01` 的驗收條件改以可在本機驗證的形式表述，並衍生 `OI-07`。
- 新增 `NFR-SEC-06`（送往 Claude API 的資料最小化），並衍生 `OI-06`（資料外送合規與費用歸屬，尚未決定）。
- `FR-CHT-01`、`FR-CHT-03` 依區塊方案改寫身分傳遞的驗收條件。

## 1. 系統概述

### 1.1 系統名稱

University AI Smart Course Assistant（暫定）。

### 1.2 系統目的

建立一套 AI 課程助理，讓單一大學內的老師、學生與管理員能更有效率地處理課綱、課程、行事曆、通知、摘要與課程問答。系統不取代既有的學習管理系統，而是在其之上補足 AI 能力。

### 1.3 系統範圍

**範圍內**：課綱分析、課程建立、行事曆建立與同步、Email 通知與提醒、每週摘要、課程聊天助理、課綱更新比對、營運狀態面板、登入與權限控制。

**明確排除**（第一版不做，避免範圍蔓延）：

- 多校／多租戶部署（見 `NFR-EXT-01`）
- 成績計算、作業批改、學生繳交作業流程
- 行動裝置原生 App
- 課綱以外的教材自動分析
- 即時語音互動
- 從外部系統反向寫回課綱

### 1.4 使用角色

| 角色   | 說明                                         | 權限來源                         |
| ------ | -------------------------------------------- | -------------------------------- |
| 老師   | 上傳課綱、確認解析結果、檢視摘要與更新提醒   | Moodle 課程層級 `editingteacher` |
| 學生   | 檢視課程內容與摘要、使用聊天助理、訂閱行事曆 | Moodle 課程層級 `student`        |
| 管理員 | 管理帳號權限、檢視系統運作與通知同步狀態     | Moodle 站台層級 `manager`        |

三個角色的權限一律由 Moodle 既有的角色與課程脈絡決定，外掛不另建身分體系。課綱相關操作皆發生在**已存在的課程脈絡內**（`D-10`），因此老師的權限來源始終是課程層級的 `editingteacher`，不需要站台層級的授權。

### 1.5 系統價值

減少老師手動整理課綱與課程資料的時間，降低通知與同步的人為錯誤，並讓學生更快取得正確的課程資訊。

### 1.6 名詞定義

BDD 場景撰寫時一律使用下列詞彙，避免同義詞造成 step definition 分裂。

| 詞彙       | 定義                                                       |
| ---------- | ---------------------------------------------------------- |
| 課綱       | 老師上傳的原始課程大綱檔案，以及其解析後的結構化資料       |
| 課綱版本   | 同一門課的課綱每次重新上傳即產生一個新版本，版本號單調遞增 |
| 課程       | Moodle 中的一門課（course）。課綱上傳時課程即已存在，系統負責填入其內容（`D-10`） |
| 週次       | 課程中的一個教學週，對應 Moodle 的課程章節（section）      |
| 課程事件   | 有日期的待辦項目，型別為作業、考試、專題或其他             |
| 解析結果   | 課綱經 AI 抽取後、尚未經老師確認的結構化資料               |
| 已確認課綱 | 老師確認後的解析結果，是下游功能唯一可用的資料來源         |
| 通知       | 送達使用者的訊息，一律經由 Moodle 送出（見 `D-02`）        |
| 排程任務   | 外掛註冊於 Moodle Task API、依設定時間自動執行的工作       |
| 臨機任務   | 外掛排入 Moodle 工作佇列、於背景執行一次的工作             |

## 2. 架構前提與決策

### 2.1 技術選型

系統以 Moodle 外掛套組的形式交付（`D-07`），全部執行於 Moodle 站台之內，不依賴外部服務。

| 層     | 元件                        | 職責                                                                     |
| ------ | --------------------------- | ------------------------------------------------------------------------ |
| 平台   | Moodle 5.2（`D-09`）        | 使用者、角色、課程、選課、檔案、行事曆、通知寄送、操作紀錄、排程與背景工作 |
| 介面   | `block_universityai`        | 課程頁面內的聊天區塊（`D-06`）                                            |
| 核心   | `local_universityai`        | 課綱上傳與確認介面、課程與章節建立、排程任務、事件觀察者、設定頁          |
| AI 存取 | `aiprovider_claude`         | 透過 Moodle AI 子系統呼叫 Claude API（`D-05`）                            |
| 資料   | Moodle 資料庫（外掛專屬表） | 僅存 Moodle 原本沒有的資料：解析結果與版本、AI 產出與引用、營運狀態       |
| 開發工具 | Python 評測工具鏈          | 不隨外掛發行。課綱測試集的正確率量測（`FR-SYL-02`），見 §2.5              |

**編排由 Moodle Task API 負責**，不使用 n8n：排程任務（scheduled task）處理每週摘要與定期比對，臨機任務（adhoc task）處理課綱解析的非同步執行與失敗重試，事件觀察者（event observer）取代外部事件推送。此為 `D-07` 的直接結果，理由見該決策。

### 2.2 決策紀錄

以下十項為本版採用的架構決策。若任一項被推翻，須回頭修改所標註的需求。`D-07` 是其中影響最廣的一項，並改寫了 `D-02`、`D-04` 的部分內容。

**D-01　Moodle 為唯一資料真相來源**
課程、使用者、選課、行事曆、通知狀態一律以 Moodle 為準，自建服務不保存副本。
*理由*：避免雙向同步與衝突解決，該工作量大且對系統價值無貢獻。
*若推翻*：`FR-CRS-01`、`FR-CAL-01`、`FR-AUT-01` 須改寫，並新增同步衝突處理需求。

**D-02　所有對使用者的通知一律由 Moodle 訊息系統送出**
外掛只負責判斷通知對象與時機，實際送達交由 Moodle 的 Message API。
*理由*：繼承站台 SMTP 設定與使用者通知偏好，不需自行保管學生 Email，並取得單一稽核軌跡。
*若推翻*：`FR-NTF-01`~`FR-NTF-04`、`NFR-SEC-03` 須改寫。

**D-03　學生端行事曆同步採 iCal 訂閱，不採 per-student OAuth**
學生自 Moodle 取得 iCal 訂閱網址，貼入自己的 Google 或 Outlook 行事曆。老師端如需寫入個人 Google Calendar，由外掛的臨機任務單獨處理。
*理由*：開發量為零，且同時滿足 Google 與 Outlook 兩項需求。per-student OAuth 需處理同意畫面審核與 token 保管，投入產出比不成立。
*若推翻*：`FR-CAL-02`、`FR-CAL-03` 須改寫，並新增 OAuth token 保管需求。

**D-04　一切執行環境皆以 Docker 提供，資料掛載於專案目錄下**
Moodle、資料庫、PHP／Composer、測試工具、Behat 瀏覽器、信件攔截、Python 評測工具鏈一律容器化；**開發者主機除 Docker 與 GNU Make 外不安裝任何專案相依**。展示時亦為本機環境，不依賴學校正式站台與校內網路。
*理由*：外掛開發需要一個可自由安裝與重裝外掛的站台，學校正式站台不會開放。全面容器化則讓環境可在任何機台重建，這對「換一台機器展示」與多人協作同時有效。
*掛載位置*：Moodle 原始碼、外掛原始碼、`moodledata`、設定檔與匯出的資料庫傾印皆置於專案目錄下（見 §2.5），使整個專案可整包複製到另一台機器。
*一項例外*：**資料庫的資料目錄不採專案目錄掛載，改用具名磁碟區**。跨機器複製資料庫實體檔案在版本、位元組序與檔案鎖上都不可靠，Windows 主機上掛載資料庫資料目錄更是已知的權限與效能痛點。可攜性改由 `make db-dump` 產出 SQL 傾印到專案目錄達成——這才是實際可用的搬移方式。若堅持整包掛載，須自行承擔換機時資料庫起不來的風險。
*代價*：本機站台無公開網址，連帶產生兩項限制——外部行事曆服務無法抓取本機的 iCal 網址（見 `FR-CAL-02`），且 Moodle 無可用的對外寄信管道（見 `FR-NTF-01`）。兩者皆已反映在對應需求的驗收條件中。
*註*：本項原本還承擔「安裝 `local_wsmanagesections` 與 `tool_trigger` 兩個第三方外掛」的理由，`D-07` 之後兩者皆不再需要（見該決策）。n8n 亦已退出架構，本機環境只需 Moodle、資料庫與信件攔截服務三個容器。
*若推翻*：改用他人維護的站台時，須確認能安裝自製外掛；否則整個 `D-07` 不成立。

**D-05　語言模型採用 Anthropic Claude API；生成類功能走 Moodle AI 子系統，結構化抽取走外掛自有介面**
所有需要語言模型的功能一律由自製的 `aiprovider_claude` 呼叫 Claude API，但**呼叫路徑分為兩條**：

| 用途                         | 路徑                                                            | 對應需求                              |
| ---------------------------- | --------------------------------------------------------------- | ------------------------------------- |
| 摘要生成、差異說明、課程問答 | Moodle AI 子系統的 `generate_text` 與 `summarise_text` 動作      | `FR-SUM-01`、`FR-DIF-03`、`FR-CHT-01` |
| 課綱結構化抽取               | `local_universityai` 自訂的抽取介面，由 `aiprovider_claude` 實作 | `FR-SYL-02`                           |

*為何必須分兩條路*——以下為 Moodle 5.2 原始碼的查證結果，非依文件推測：

1. **核心動作只有四個**（`generate_text`、`summarise_text`、`explain_text`、`generate_image`），而 `generate_text` 的建構子簽章僅有 `(int $contextid, int $userid, string $prompttext)`——**沒有任何位置可傳入 JSON Schema 或回應格式**，其 `store()` 也只保存純文字。子系統的動作模型在設計上就不涵蓋結構化輸出。
2. **自定義動作不被支援**。`\core_ai\manager` 至少三處把命名空間寫死為 `core_ai\aiactions\`：組裝回應類別時（`process_action()`）、設定動作啟用狀態時（`set_action_state()`）、讀取課程模組層級啟用清單時。外掛即使自行定義動作類別，也無法經標準管理介面啟用與設定。硬走這條路等於依賴未公開的內部行為，與 `NFR-MNT-04`（上架審查）直接衝突。

*理由（採用 Claude 的部分不變）*：Claude API 原生支援結構化輸出，可綁定 JSON Schema 直接產生符合 `DM-SYLLABUS` 的結果，這是 `FR-SYL-02` 得以驗收的前提。
*為何不沿用現成的 `aiprovider_openaicompatible`*：Anthropic 雖提供 OpenAI 相容層，但官方文件明載其用途為測試與比較、不建議正式使用，且不含結構化輸出等完整功能。
*附帶價值*：Moodle 5.2 核心內建的六個供應商為 `openai`、`azureai`、`gemini`、`awsbedrock`、`deepseek`、`ollama`，**沒有 Anthropic**。`aiprovider_claude` 本身即為可獨立上架的貢獻。
*對可替換性的實際影響*：見 `NFR-EXT-03`。生成類功能換供應商為零改動；抽取類功能則需該供應商實作抽取介面，或退回**通用實作**（以提示詞要求 JSON、在 PHP 端驗證 schema 並於失敗時重試）。這條退路必須隨第一版一起實作，否則 `NFR-EXT-03` 只是紙上承諾，`OI-06` 的延後也就失去依據。
*備註*：第一版預設模型 `claude-opus-5`；模型名稱、effort 與 API 金鑰皆為站台設定項，不寫死於程式（見 `NFR-EXT-03`、`NFR-MNT-01`）。
*未解*：課綱內容送出校外是否合規、費用由誰負擔，第一版先不處理，見 `OI-06`。
*若推翻*：改用其他供應商時，抽取一律走通用實作，`FR-SYL-02` 的正確率須重新量測。

**D-06　聊天助理以 Moodle 區塊（block）嵌入課程頁面**
不做獨立入口網站，不使用外部連結。
*理由*：區塊執行於 Moodle 之內，能取得使用者的登入狀態與選課關係，這正是 `FR-CHT-03` 需要的身分依據，且是三個候選方案中唯一能自然解決權限問題的。
*簡化*：`D-07` 之後聊天服務也在 Moodle 內，區塊可直接使用 Moodle 的權限檢查（`require_login`、`is_enrolled`），不再需要跨服務簽發與驗證憑證。
*若推翻*：`FR-CHT-03` 須改寫身分取得方式，並重新評估其可行性——外部連結與 iframe 皆無法自動取得 Moodle 身分。

**D-07　系統以 Moodle 外掛套組交付，並以能上架 Moodle 外掛目錄為結構前提**
交付物為三個外掛：`local_universityai`（核心邏輯、介面、排程任務、事件觀察者、設定頁）、`block_universityai`（課程頁面聊天區塊）、`aiprovider_claude`（Claude 供應商）。第一版不強求實際送審，但從一開始就遵守上架規範，避免日後大幅重構。
*理由*：使用者要求外掛形式且保留未來上架的可能。更重要的是，外掛執行於 Moodle 行程內，可直接呼叫 Moodle 內部 PHP API，不受外部 Web Service 介面的限制。
*連帶消除的三項依賴*：
　1. `local_wsmanagesections` 不再需要——第三方外掛之所以存在，是因為對外的 Web Service 缺少章節函式；外掛在內部可直接呼叫課程與章節 API（`FR-CRS-02`）。
　2. `tool_trigger` 不再需要——外掛可自行註冊事件觀察者接收 Moodle 事件（`FR-NTF-03`）。
　3. n8n 退出架構——排程、非同步執行與重試改用 Moodle Task API（scheduled task／adhoc task），這是外掛的標準做法，也是上架的必要條件（外掛不能要求站台另行架設 n8n 伺服器）。
*上架規範帶來的約束*：與 Moodle 核心介接的檔案須採 GPL v3 或更新版本授權；每個檔案須有標準檔頭與 `@copyright` 標註；需有公開的原始碼倉庫與問題回報管道；需支援至少一個仍在維護的 Moodle 版本。這些是文件與流程成本，不是技術難度，但補做比一開始就遵守貴得多。
*代價*：主要開發語言由 Python 轉為 PHP。既有的 FastAPI 程式與 pytest-bdd 測試不再是產品的一部分（見 `OI-05` 與 §2.5）。
*若推翻*：回到「外掛薄殼＋外部 Python 服務」的形式，則 `FR-CRS-02` 需重新引入 `local_wsmanagesections`、`FR-NTF-03` 需重新引入 `tool_trigger` 或改為輪詢，並須新增跨服務身分憑證的需求（原 `FR-CHT-03` 的舊版驗收條件）。

**D-08　分層採 MVVM，但以 Moodle Output API 既有的機制實現，不另建框架**
模型（Model）／視圖模型（ViewModel）／視圖（View）三層對應到 Moodle 既有結構，不引入第三方 MVC 或 MVVM 框架。

| 層         | 在外掛中的落點                                                          | 職責                                                     |
| ---------- | ----------------------------------------------------------------------- | -------------------------------------------------------- |
| Model      | `classes/` 下的領域與持久化類別（`DM-SYLLABUS` 等結構、資料表存取）     | 業務規則與資料，不知道任何呈現方式                       |
| ViewModel  | 實作 `renderable` 與 `templatable` 的類別，其 `export_for_template()`    | 把模型攤平成模板可直接使用的簡單型別，決定顯示什麼、怎麼排 |
| View       | `templates/*.mustache`                                                   | 只做呈現，不含邏輯                                       |
| 進入點     | 頁面腳本、`classes/external/`、`classes/task/`                           | 接收請求、檢查權限、呼叫模型、交給 renderer               |

*理由*：Moodle 的 `export_for_template(renderer_base $output)` 的職責定義——把 renderable 內的資料攤平成模板可用的簡單型別——與視圖模型完全一致，而 Mustache 本身是無邏輯模板語言，天然就是被動的視圖。採用既有機制而非自建框架，同時滿足 `D-07` 的上架規範（審查者預期看到標準結構）與 `NFR-MNT-02` 的模組邊界。
*一項必須說清楚的落差*：MVVM 的定義性特徵是資料繫結（視圖隨視圖模型自動更新）。Mustache 是一次性渲染，伺服器端這一側**沒有繫結**，因此伺服器端是「MVVM 的分層」而非完整的 MVVM。真正具備繫結性質的只有 `block_universityai` 的聊天前端：AMD 模組持有對話狀態作為視圖模型，狀態改變時以 `Templates.render()` 重繪片段。文件與口試說明應照此區分，不要籠統宣稱整個系統是 MVVM。
*若推翻*：若改用自建的 MVC 分派器或第三方框架，`NFR-MNT-04`（符合上架規範）將難以通過——非標準結構是外掛審查最常見的退件原因之一。

**D-09　目標 Moodle 版本釘為 5.2**
開發、測試與展示一律使用 Moodle 5.2，外掛的 `$plugin->requires` 以 5.2 為下限。5.3 LTS 發布後再評估是否加列支援。

*版本現況（查於 2026-08）*：

| 版本       | 發布       | 一般支援結束 | 安全性支援結束 |
| ---------- | ---------- | ------------ | -------------- |
| 4.5（LTS） | 2024-10-07 | 2025-10-06   | 2027-10-04     |
| 5.0        | 2025-04-14 | 2026-04-20   | 2026-10-05     |
| 5.1        | 2025-10-06 | 2026-10-05   | 2027-04-19     |
| **5.2**    | 2026-04-20 | 2027-04-19   | 2027-10-04     |
| 5.3（LTS） | 2026-10-05 | 2027-10-04   | 2029-10-01     |

*理由*：5.2 是目前的最新穩定版，一般支援延續至 2027-04，涵蓋整個專題期程。現行 LTS 為 4.5，看似穩妥，但其一般支援已於 2025-10 結束、僅剩安全性修補，**且其 AI 子系統是初版實作**——4.5 核心只內建 `openai` 與 `azureai` 兩個供應商、動作只有三個，且完全沒有供應商執行個體（provider instance）的建立與管理 API，那整套介面是 5.x 才有的。押 4.5 等於對著一套已被改寫的 API 開發 `aiprovider_claude`。下一個 LTS 是 5.3，預定 2026-10 發布，現在無法拿來開發；而 5.2 正是它的前一版，屆時升版差距最小。
*連帶事實*：**Moodle 自 5.1 起把網站根目錄移入 `public/`**。三個外掛的安裝路徑因此為 `public/local/universityai`、`public/blocks/universityai`、`public/ai/provider/claude`，網頁伺服器的 document root 指向 `public/`。這直接影響 `D-04` 的容器掛載路徑（見 §2.5），也是照舊版教學文件操作時最容易踩到的落差。
*若推翻*：改押 5.3 LTS 須等到 2026-10 之後才能開始，時程上不可行；改押 4.5 則須依舊版供應商介面重寫 `aiprovider_claude`，並回頭確認結構化抽取的退路是否仍成立。

**D-10　課綱於既有課程內上傳，系統填入課程內容而非建立課程**
課程外殼由老師或管理員依 Moodle 既有流程建立（空課即可），老師進入該課程後上傳課綱，系統負責填入課程資訊、建立週次章節與課程事件。

*理由*：原本「由課綱長出一門課」的流程在權限上站不住腳。§1.4 定義老師的權限來源是**課程層級**的 `editingteacher`，課程不存在時這個人在系統中沒有任何角色，權限檢查無從做起；而「誰能建立課程」在 Moodle 本來就屬站台管理權限，外掛若自行開一條建課路徑，等於繞過核心權限模型，與 `NFR-SEC-01` 衝突，也是上架審查會挑的問題。此外 `FR-SYL-01` 要求原始檔案存於課程檔案區，課程不存在時根本無處可存——這是舊版需求的內在矛盾。
*代價*：展示時多一個「先建立空課程」的手動步驟，「自動建課」的敘事縮小為「自動填課」。這是為了換取權限模型的正確性，值得。
*連帶簡化*：`DM-SYLLABUS` 的 `course_ref` 不再有 null 狀態；`FR-CRS-01` 由「建立課程」改為「填入課程資訊」；`FR-CRS-02` 不再需要與課程建立共用交易邊界。
*若推翻*：改回站台層級上傳，須新增站台層級的自訂 capability、設計課程建立的權限規則，並為上傳檔案安排課程建立前的暫存位置（使用者私人檔案區），`FR-SYL-01`、`FR-CRS-01`、`NFR-SEC-01` 皆須改寫。

### 2.5 開發工具約定

`D-07` 之後產品程式碼為 PHP，Python 不再位於執行路徑上，但仍保留於開發工具鏈：

| 用途                                     | 語言／工具         | 是否隨外掛發行 |
| ---------------------------------------- | ------------------ | -------------- |
| 外掛本體（三個外掛）                     | PHP                | 是             |
| 外掛單元測試                             | PHPUnit            | 是（`tests/`） |
| 外掛驗收測試                             | Behat              | 是（`tests/behat/`） |
| 課綱解析正確率評測（`FR-SYL-02` 的驗收） | Python             | 否             |
| 測試課綱的整理與人工標註輔助             | Python             | 否             |

**Python 相依一律以 uv 管理**，且在容器內執行（`D-04`）。以 `pyproject.toml` 與 `uv.lock` 取代現行的 `requirements.txt`；鎖檔須進版控，讓正確率量測的結果可被重現——這是 `FR-SYL-02` 驗收數字有意義的前提。現行 `requirements.txt` 內含大量與評測無關的相依（FastAPI、Flask、uvicorn 等），遷移時只保留評測工具鏈實際需要的部分。

> 評測工具不隨外掛發行，因此不受 `D-07` 的上架規範約束，語言與相依可自由選擇。選 Python 是因為 PDF 文字處理與資料分析的生態較成熟，且既有程式已有可重用的部分。

#### 容器組成與掛載配置

依 `D-04`，執行環境由下列容器構成，主機端不安裝 PHP、Composer、Node 或 Python：

| 容器           | 用途                                          | 專案目錄掛載                              |
| -------------- | --------------------------------------------- | ----------------------------------------- |
| `moodle`       | 網頁伺服器與 PHP，跑 Moodle 5.2 與三個外掛    | 外掛原始碼分別掛入 `public/local/universityai`、`public/blocks/universityai`、`public/ai/provider/claude`；`moodledata` |
| `db`           | 資料庫                                        | **不掛載資料目錄**，改用具名磁碟區（見 `D-04` 例外說明）；傾印檔輸出至專案目錄 |
| `mail`         | 信件攔截，作為 Moodle 的 SMTP 目標            | 無                                        |
| `selenium`     | Behat 驗收測試所需的瀏覽器                    | 無                                        |
| `tools`        | Composer、PHPUnit、Behat、`moodle-plugin-ci`  | 專案根目錄                                |
| `eval`         | Python 評測工具鏈（uv）                       | 測試課綱、標註檔與量測結果                |

> Behat 需要真實瀏覽器驅動，因此 `selenium` 容器是必要的而非選配；另需為 Behat 配置獨立的 dataroot 與資料表前綴，避免污染開發用資料。這兩點常在第一次跑測試時才被發現，架構文件應預先寫明。
>
> **document root 為 `public/` 而非 Moodle 目錄本身**（`D-09`）。網頁伺服器設定與外掛掛載路徑都須照此，網路上多數 Docker 教學仍是 5.0 以前的扁平結構，直接照抄會得到 404。

**版控與隱私**：`moodledata`、資料庫傾印、`eval` 的測試課綱與標註檔一律加入 `.gitignore`。`moodledata` 會存放老師上傳的課綱原檔，可能含授課教師姓名與聯絡方式（見 `OI-03` 的去識別化說明），不得進版控。

#### Makefile 為唯一操作入口

所有開發、測試、建置與展示指令一律經由 Makefile，各目標的內容是 `docker compose` 呼叫，主機端只需 Docker 與 GNU Make。至少須提供：

| 目標                       | 作用                                                   |
| -------------------------- | ------------------------------------------------------ |
| `make up` / `make down`    | 啟動／停止整套環境                                     |
| `make install`             | 首次安裝 Moodle 並啟用三個外掛                         |
| `make logs` / `make shell` | 檢視記錄／進入容器                                     |
| `make lint`                | 執行 `moodle-plugin-ci` 的程式碼檢查（`NFR-MNT-04`）    |
| `make test`                | PHPUnit 單元測試                                       |
| `make behat`               | Behat 驗收測試                                         |
| `make db-dump` / `db-restore` | 匯出／還原資料庫傾印，這是換機展示的搬移方式（`D-04`） |
| `make eval`                | 執行課綱解析正確率量測（`FR-SYL-02`）                  |

> **Windows 主機注意**：GNU Make 不隨 Windows 內建，須另行安裝（winget、scoop 或 WSL 皆可）。這是主機端唯一需要 Docker 以外的安裝項目，架構文件的環境準備步驟應寫明。

## 4. 功能需求

### 4.1 課綱分析

#### FR-SYL-01　接收課綱檔案

**來源** 平台　**版本** 必要　**相依** `D-10`

系統應在**既有課程的脈絡內**提供課綱上傳介面，接受老師上傳課綱檔案，並在接收時檢查格式限制。

第一版**僅支援**含文字層的 PDF 與 DOCX，且日期須為西元格式。掃描影像 PDF、民國年日期、以圖片呈現的表格不在第一版支援範圍。

**驗收條件**

- 上傳介面位於課程脈絡內，僅具該課程 `editingteacher` 能力者可存取；學生與其他課程的老師存取時一律被拒（`FR-AUT-01`）。
- 上傳支援格式的檔案時，系統接受並回傳可追蹤的課綱識別碼，且該識別碼自始即繫結所屬課程。
- 上傳不支援的格式時，系統拒絕並明確告知支援哪些格式，不得只回傳「上傳失敗」。
- 上傳無文字層的 PDF 時，系統在解析前即偵測並告知原因（`NFR-USA-03`）。
- 上傳的原始檔案保留於該課程的檔案區，供日後查核。

#### FR-SYL-02　抽取課程結構

**來源** 自建　**版本** 必要　**相依** `DM-SYLLABUS`、`D-05`

系統應從課綱文字中抽取課程名稱、學期資訊、週次與日期、課程事件（作業、考試、專題）、評分方式，並輸出為 `DM-SYLLABUS` 結構。

**驗收條件**

- 輸出於 PHP 端通過 `DM-SYLLABUS` 的 JSON Schema 驗證後才得寫入；驗證失敗即重試，連續失敗達上限則記為失敗並保留原始回應供查核（`NFR-REL-02`）。此驗證不因供應商是否原生支援結構化輸出而省略。
- 抽取介面須有兩個可切換的實作：`aiprovider_claude` 的原生結構化輸出實作，以及以提示詞要求 JSON 的通用實作。兩者皆須通過上述驗證（`D-05`、`NFR-EXT-03`）。
- 以不少於 20 份真實課綱組成的測試集量測，週次日期抽取正確率 ≥ 80%，課程事件日期抽取正確率 ≥ 80%。測試集與量測結果須隨程式碼一併保存。
- 任何無法判定的欄位須填入 `null` 並記入 `parse_meta.unresolved`，不得臆造數值（對應 §8.2）。
- 同一份課綱重複解析兩次，週次數量與各事件日期須一致。

#### FR-SYL-03　標註來源與信心

**來源** 自建　**版本** 必要

每一個抽取出的週次與課程事件，須附帶原文出處片段與信心值。

**驗收條件**

- `weeks[]` 與 `events[]` 的每個元素都具有非空的 `source_span` 與介於 0 到 1 的 `confidence`。
- `source_span` 的內容必須實際出現在課綱原文中。
- 信心值低於門檻（預設 0.6）的項目，在確認介面中須被標示出來（`FR-SYL-04`）。

#### FR-SYL-04　老師確認與修正

**來源** 自建　**版本** 必要

解析結果須經老師確認後才成為「已確認課綱」，下游功能只能使用已確認課綱。

**驗收條件**

- 解析完成後狀態為「待確認」，此時呼叫課程建立（`FR-CRS-01`）應被拒絕。
- 老師可逐項修改週次主題、日期與課程事件後再確認。
- 低信心項目與 `parse_meta.unresolved` 中的項目在介面上有明顯標示。
- 確認動作記錄確認者與時間。
- 老師修改過的欄位須標記為人工覆寫，後續重新解析不得覆蓋（`FR-DIF-02`）。

### 4.2 課程建立

#### FR-CRS-01　依課綱填入課程資訊

**來源** 平台　**版本** 必要　**相依** `D-01`、`D-10`

系統應依已確認課綱，將課程名稱、簡述與學期起訖填入該課綱所屬的既有課程。

> v1.3 以前本需求為「依課綱建立課程」。`D-10` 之後課程外殼先於課綱存在，本需求改為填入內容；課程本身的建立仍由 Moodle 既有流程負責，外掛不介入。

**驗收條件**

- 僅在課綱狀態為「已確認」時可執行，否則拒絕（`FR-SYL-04`）。
- 執行後課程的名稱、簡述與起訖日期與已確認課綱一致。
- 同一份已確認課綱重複執行，結果相同且不產生額外副作用（具冪等性）。
- 課程既有欄位若已有內容且與課綱不同，須先向老師呈現將被覆寫的項目，不得靜默蓋掉。
- 執行失敗時課程回復至執行前狀態，錯誤原因記入營運狀態（`DM-OPSTATUS`）。

#### FR-CRS-02　建立週次章節

**來源** 平台　**版本** 必要　**相依** `D-07`

系統應依課綱週次建立對應的 Moodle 課程章節，並填入該週主題與備註。

> v1.1 時本需求標為「外掛」，因對外的 Web Service 缺少章節函式而須安裝 `local_wsmanagesections`。`D-07` 之後外掛在 Moodle 行程內執行，直接呼叫課程與章節的內部 API 即可，該依賴已消除，降級路徑也不再需要。

**驗收條件**

- 建立後的章節數量等於課綱的 `term.total_weeks`。
- 第 N 個章節的名稱對應課綱 `weeks[N-1].topic`。
- 章節建立為單一交易，中途失敗不得留下部分建立的章節（`D-10` 之後不再與課程建立共用交易邊界）。

### 4.3 行事曆建立與同步

#### FR-CAL-01　建立課程事件

**來源** 平台　**版本** 必要

系統應將課綱中的課程事件建立為 Moodle 中帶有截止日的活動，使其自動出現於課程行事曆與學生時間軸。

**驗收條件**

- 課綱中每一個 `events[]` 項目在 Moodle 產生一個對應活動，且截止日一致。
- 該活動自動出現在課程行事曆，不需另外建立行事曆事件。
- 重複執行不產生重複活動。

#### FR-CAL-02　學生訂閱行事曆

**來源** 組態　**版本** 必要　**相依** `D-03`、`D-04`

學生應能取得個人行事曆訂閱網址，該網址提供符合 iCalendar 規格且內容正確的課程事件。

> **本機環境的限制與應對**：Google Calendar 的「從網址新增日曆」是由 **Google 的伺服器**去抓取訂閱網址，而非使用者的瀏覽器；因此無論用什麼工具驅動瀏覽器，Google 都到不了只存在於本機的 Moodle（`D-04`）。加上 Google 對外部 iCal 來源的重新抓取間隔不受呼叫端控制，「事件變更後自動更新」也無法現場演示。
>
> 因此本需求的驗收改為**直接驗證系統產出的 iCal 內容**——這才是系統真正該負責的部分，可完全自動化且不需任何外部服務。「事件出現在自己的 Google 行事曆」這條展示路徑改由 `FR-CAL-03` 的 API 推送承擔。

**驗收條件**

- 學生可於介面取得自己的 iCal 訂閱網址。
- 以該網址取得的內容為合法 iCalendar 格式，其中的 `VEVENT` 與該生所屬課程的課程事件一一對應，標題與截止時間一致。
- 非該生所屬課程的事件不得出現在其訂閱內容中。
- 課程事件變更後，重新取得的訂閱內容反映變更。
- 訂閱網址含存取權杖，介面須提示不可外流，且提供重設權杖的途徑；重設後舊網址即失效（`NFR-SEC-02`）。
- 展示時不得以「手動匯入一次 .ics 檔」替代訂閱，該做法無法呈現持續更新，不符本需求。

#### FR-CAL-03　寫入 Google 行事曆

**來源** 自建　**版本** 必要　**相依** `FR-CAL-04`

使用者應能授權系統將其課程事件寫入自己的 Google 行事曆，並於課程事件變更時同步更新。

> v1.3 時本需求為「目標」且僅涵蓋老師。改列「必要」並擴及學生，是因為它承接了 `FR-CAL-02` 讓不出來的展示路徑：推送方向是由本機站台**向外**呼叫 Google API，不受 `D-04` 的本機限制，事件即時出現；且 Google 允許以 `localhost` 作為 OAuth 導回網址，本機環境即可完成授權流程。

**驗收條件**

- 使用者完成 OAuth 授權後，其所屬課程的課程事件寫入指定的 Google 行事曆，標題與截止時間一致。
- 課程事件新增、修改、刪除後，對應的 Google 行事曆項目同步更新，且不產生重複項目（`NFR-REL-04`）。
- 授權失敗、逾期或遭撤銷時，系統停止嘗試寫入並通知該使用者，不得靜默失敗。
- 存取權杖與更新權杖不出現在前端與記錄檔中（`NFR-SEC-05`）。
- 寫入結果不論成敗皆留下紀錄（`FR-CAL-04`）。
- Outlook 寫入列為延後（`NFR-EXT-02`）。

#### FR-CAL-04　記錄同步結果

**來源** 自建　**版本** 必要　**相依** `DM-OPSTATUS`

每次行事曆相關寫入的結果須留下可查詢的紀錄。

**驗收條件**

- 每次寫入不論成功失敗，皆產生一筆符合 `DM-OPSTATUS` 的紀錄。
- 失敗紀錄包含可辨識原因的錯誤訊息與重試次數。

### 4.4 通知與提醒

#### FR-NTF-01　通知老師

**來源** 組態　**版本** 必要　**相依** `D-02`、`D-04`

系統應在課綱解析完成、課程建立完成、比對產生差異時通知老師。

> **本機環境限制**：本機 Docker 的 Moodle 沒有可用的對外寄信管道（`D-04`）。第一版須在 compose 中加入信件攔截服務（如 Mailpit）作為 Moodle 的 SMTP 目標，寄出的信件於其網頁介面檢視即視為送達。真實 SMTP 中繼的設定列為 `OI-07`。

**驗收條件**

- 上述事件發生後，對應老師於 Moodle 站內收到通知。
- 若該使用者的通知偏好包含 Email，對應信件出現在信件攔截服務中，且收件者、主旨、內文正確。
- 通知內容包含事件類型與可直接前往處理的連結。
- 通知一律經由 Moodle 送出，系統不另行寄信。

#### FR-NTF-02　通知學生

**來源** 組態　**版本** 必要　**相依** `D-02`

系統應在課程事件截止前與課綱更新時通知修課學生。

**驗收條件**

- 僅通知該課程的實際修課學生，不得外洩至非修課者。
- 課程事件的到期提醒由 Moodle 內建機制處理，系統不重複發送。
- 同一事件對同一使用者不得重複發送（去重）。

#### FR-NTF-03　事件觸發

**來源** 平台　**版本** 必要　**相依** `D-07`

Moodle 內特定事件發生時應觸發對應處理。

> v1.1 時本需求標為「外掛」且版本為「目標」，因需安裝 `tool_trigger` 之類的第三方外掛把事件推送到外部。`D-07` 之後外掛自行註冊事件觀察者即可接收，實作成本大幅降低，故升為「必要」。

**驗收條件**

- 老師完成上傳後，解析工作以臨機任務排入佇列，不阻塞上傳請求（`NFR-PRF-01`）。
- 事件觀察者只負責排入任務，不在觀察者內執行耗時工作。
- 佇列中的任務失敗時由 Moodle Task API 自動重試（`NFR-REL-01`）。

#### FR-NTF-04　課綱更新提醒

**來源** 自建　**版本** 目標　**相依** `FR-DIF-01`

課綱比對產生重大差異時，應通知老師與該課程學生。

**驗收條件**

- 僅 `severity` 為 `major` 的差異觸發學生通知；`minor` 差異僅通知老師。
- 通知內容包含變更項目清單，而非僅告知「課綱已更新」。

### 4.5 每週摘要

#### FR-SUM-01　生成並發布每週摘要

**來源** 自建　**版本** 必要

系統應每週自動生成課程摘要，內容涵蓋本週重點、下週重點與待辦提醒，並發布於課程中供師生檢視。

**驗收條件**

- 以 Moodle 排程任務於設定的時間自動執行，不需人工觸發；執行頻率可由站台管理員在排程設定中調整。
- 摘要內容僅根據已確認課綱與課程事件產生，不得引入課綱以外的資訊。
- 摘要包含本週重點、下週重點、七日內到期的課程事件三個區塊。
- 課程若無當週資料，發布明確的「本週無安排」而非空白內容。
- 產生的摘要保留版本與生成時間（§8.2）。

### 4.6 聊天助理

#### FR-CHT-01　課程問答

**來源** 自建　**版本** 目標　**相依** `D-06`、`D-07`

系統應以 `block_universityai` 區塊的形式，在課程頁面內提供聊天介面，依據已確認課綱與課程資料回答學生問題。

**驗收條件**

- 聊天介面出現在課程頁面內，學生不需另行登入。
- 回答僅根據檢索到的課程資料產生。
- 每則回答附上可驗證的出處（課綱段落或課程事件）。
- 以固定的評測題組量測，回答正確率與拒答適當性須被記錄。

#### FR-CHT-02　無依據時拒答

**來源** 自建　**版本** 目標

當檢索不到足以支撐回答的資料時，系統應明確拒答，不得臆測。

**驗收條件**

- 問題超出課程資料範圍時，回覆明確表示無法從課程資料中找到答案。
- 拒答時不附上不相關的出處充數。
- 評測題組須包含至少五題刻意無解的問題，全數須正確拒答。

#### FR-CHT-03　查詢範圍限制

**來源** 平台　**版本** 必要　**相依** `D-06`、`D-07`

學生僅能查詢自己實際修習之課程的資料。

> 草案未涵蓋此需求。v1.1 時它是本專案風險最高的項目之一，因為聊天服務位於 Moodle 之外，必須自行設計跨服務的身分憑證。`D-07` 之後聊天邏輯執行於 Moodle 行程內，改用 Moodle 既有的權限檢查即可，風險大幅下降，故由「目標」升為「必要」。

**驗收條件**

- 每次查詢前皆檢查登入狀態與該課程的存取權（`require_login` 與課程脈絡的權限檢查），未通過者不得取得任何課程資料。
- 檢索範圍限定於當前課程脈絡，不得跨課程檢索。
- 學生被取消選課後，立即失去該課程的問答存取權（與 `FR-AUT-02` 同一機制，不另行維護權限副本）。
- 前端傳入的課程識別碼一律重新驗證，不得直接採信。

### 4.7 課綱更新比對

#### FR-DIF-01　偵測版本差異

**來源** 自建　**版本** 目標　**相依** `DM-DIFF`

同一門課上傳新版課綱時，系統應比對前後版本並產出差異清單。

**驗收條件**

- 比對在已解析的結構化資料上進行，逐欄位判定，不得以整份原文交由語言模型比較。
- 差異結果符合 `DM-DIFF` 結構，每項標明欄位路徑、舊值、新值與嚴重度。
- 影響日期或評分比重的變更判定為 `major`，純文字敘述調整判定為 `minor`。
- 新增與刪除的課程事件皆須被偵測到，不得只回報修改。

#### FR-DIF-02　保留人工覆寫

**來源** 自建　**版本** 目標　**相依** `FR-SYL-04`

老師手動修改過的欄位，在新版課綱解析後不得被自動覆蓋。

**驗收條件**

- 人工覆寫過的欄位在比對結果中被標示，並要求老師逐項決定是否採用新值。
- 未經老師決定前，已確認課綱維持原值。

#### FR-DIF-03　差異說明

**來源** 自建　**版本** 目標

系統應將差異清單轉為可讀的說明文字。

**驗收條件**

- 說明文字中提及的每項變更，皆能對應到 `DM-DIFF` 中的實際項目，不得增添未發生的變更。
- 差異清單為空時不產生說明文字。

### 4.8 狀態面板

#### FR-DSH-01　課程總覽

**來源** 組態　**版本** 必要

師生應能總覽自己的課程與近期待辦。

**驗收條件**

- 使用 Moodle 既有的儀表板與時間軸，不另行開發重複介面。
- 由 `FR-CAL-01` 建立的課程事件出現在使用者時間軸中。

#### FR-DSH-02　營運狀態

**來源** 自建　**版本** 目標　**相依** `DM-OPSTATUS`

管理員應能查看通知、同步與課綱解析的執行狀態。

**驗收條件**

- 呈現每項任務最近執行的結果、失敗筆數與失敗原因。
- 資料來自外掛自行落地的 `DM-OPSTATUS` 紀錄，呈現於外掛的管理頁面；不要求管理員自行判讀 Moodle 的任務記錄檔。
- 僅具站台管理權限者可存取。

### 4.9 登入與權限

#### FR-AUT-01　角色登入

**來源** 組態　**版本** 必要　**相依** `D-01`

老師、學生、管理員應以各自帳號登入，系統依角色顯示不同功能。

**驗收條件**

- 身分驗證由 Moodle 負責，系統不自行保管密碼。
- 未登入者存取任何功能一律導向登入。
- 學生無法存取課綱上傳與確認功能。
- 非管理員無法存取營運狀態面板（`FR-DSH-02`）。

#### FR-AUT-02　權限一致性

**來源** 自建　**版本** 必要

自建服務的存取控制須與 Moodle 的課程權限一致。

**驗收條件**

- 使用者在 Moodle 被取消選課後，即失去該課程資料的存取權。
- 自建服務不得存在繞過 Moodle 權限的後門端點。
- 服務間呼叫使用專屬憑證，且該憑證不出現在前端（`NFR-SEC-01`）。

## 5. 資料模型

本節定義的結構是各功能之間的契約，變更視同需求變更。

### DM-SYLLABUS　課綱解析結果

```jsonc
{
  "syllabus_id": "uuid",
  "course_ref": "Moodle 課程 id，上傳時即已繫結（D-10）",
  "version": 1,                       // 每次重新上傳遞增
  "status": "parsed | confirmed",     // 見 FR-SYL-04
  "course": {
    "title": "string",
    "code": "string | null",
    "teacher": "string | null",
    "semester": "string | null",      // 例：114-1
    "credits": "number | null"
  },
  "term": {
    "start_date": "YYYY-MM-DD",
    "total_weeks": 18,
    "weekday": "MON | TUE | ... | SUN | null"
  },
  "grading": [
    { "item": "期中考", "weight": 30, "note": "" }
  ],
  "weeks": [
    {
      "week_no": 1,
      "date": "YYYY-MM-DD",
      "topic": "string",
      "note": "string",
      "confidence": 0.0,              // FR-SYL-03
      "source_span": "原文片段",       // FR-SYL-03
      "overridden": false             // FR-DIF-02
    }
  ],
  "events": [
    {
      "event_id": "string",
      "type": "assignment | exam | project | other",
      "title": "string",
      "due_date": "YYYY-MM-DD",
      "due_time": "HH:MM | null",
      "week_no": "integer | null",
      "confidence": 0.0,
      "source_span": "原文片段",
      "overridden": false
    }
  ],
  "parse_meta": {
    "source_file": "string",
    "parsed_at": "ISO-8601",
    "model": "string",                // §8.2 保留來源
    "unresolved": ["無法判定的項目描述"]
  }
}
```

**約束**

- `weeks[].week_no` 於同一課綱內唯一且連續。
- `weeks` 長度等於 `term.total_weeks`。
- `events[].due_date` 須落在學期起訖範圍內，否則列入 `parse_meta.unresolved`。
- `grading[].weight` 總和若不等於 100，須列入 `parse_meta.unresolved`，不得自動調整。

### DM-DIFF　版本差異

```jsonc
{
  "diff_id": "uuid",
  "syllabus_id": "uuid",
  "from_version": 1,
  "to_version": 2,
  "changes": [
    {
      "path": "weeks[3].topic",
      "kind": "added | removed | modified",
      "old": "任意型別 | null",
      "new": "任意型別 | null",
      "severity": "major | minor",     // FR-DIF-01
      "was_overridden": false          // FR-DIF-02
    }
  ],
  "summary_text": "供人閱讀的說明，由 changes 產生",  // FR-DIF-03
  "generated_at": "ISO-8601"
}
```

**嚴重度判定規則**：異動 `term`、`weeks[].date`、`events[].due_date`、`grading[].weight` 或新增／刪除 `events` 者為 `major`；其餘為 `minor`。

### DM-OPSTATUS　營運狀態紀錄

```jsonc
{
  "record_id": "uuid",
  "operation": "syllabus_parse | course_populate | event_create | calendar_push | weekly_summary | notify",
  "target_type": "syllabus | course | event | user",
  "target_id": "string",
  "status": "success | failed | retrying",
  "attempt": 1,
  "error": "string | null",
  "occurred_at": "ISO-8601"
}
```

> v1.3 時本結構的第一個欄位名為 `workflow`，是 n8n 時期的遺留字。`D-07` 之後架構中已無「工作流」這一層，且 §1.6 的用語為排程任務與臨機任務，故改名為 `operation`；其值同時涵蓋任務與非任務的操作（如通知送出）。此欄位即將成為實際資料表欄位，趁尚未建表時更名。

#### NFR-SEC-06 的具體規則

「不夾帶個資」若只寫成一句宣示，實作時無從判定也無從驗收，故在此展開為可檢查的規則。

**白名單**——只有下列內容得以送出，其餘一律不送：課綱檔案的文字內容、已確認課綱的結構化欄位、課程名稱與簡述、課程事件的標題與日期、使用者在聊天介面自行輸入的提問文字。

**黑名單**——下列項目即使出現在白名單內容之中，也須於送出前移除：姓名、學號、Email、電話、住址、Moodle 使用者 id 與 IP 位址、成績與作業內容。

**去識別化規則**

- 授課教師姓名與聯絡方式須在**進入解析之前**即自課綱原文中移除。此規則與 `OI-03` 測試集去識別化共用同一份實作，不得各寫一套——兩邊規則若分歧，量測結果就無法代表正式流程的行為。
- 需要在提示詞中指涉使用者時，一律使用課程脈絡內的臨時代號，不得送出可跨課程或跨時間串接的識別碼。
- 使用者自行輸入的提問文字無法事先保證不含個資，因此介面須提示「請勿輸入個人資料」。這是提示義務，不構成放寬其他欄位的理由。

**驗收條件**

- 過濾為獨立元件，不與提示詞組裝邏輯混寫，可單獨測試。
- PHPUnit 以刻意含個資的樣本驗證：過濾後的輸出不含任何黑名單項目。
- 所有送往語言模型的路徑（生成類與抽取類，見 `D-05`）皆經同一個過濾元件，不存在繞過路徑。
- 記錄檔與 `DM-OPSTATUS` 中保存的請求內容為過濾後版本。

## 7. 系統流程

### 7.1 主流程

0. 課程外殼依 Moodle 既有流程建立（`D-10`，不在系統範圍內）。
1. 使用者經 Moodle 登入（`FR-AUT-01`）。
2. 老師在該課程內上傳課綱（`FR-SYL-01`）。
3. 系統非同步解析並標註來源與信心（`FR-SYL-02`、`FR-SYL-03`、`NFR-PRF-01`）。
4. 老師確認或修正解析結果（`FR-SYL-04`）。
5. 系統填入課程資訊並建立週次章節（`FR-CRS-01`、`FR-CRS-02`）。
6. 系統建立帶截止日的課程事件，行事曆自動生成（`FR-CAL-01`）。
7. 使用者訂閱個人行事曆，或授權推送至 Google 行事曆（`FR-CAL-02`、`FR-CAL-03`）。
8. 系統於事件到期前發出提醒（`FR-NTF-02`）。
9. 系統每週生成並發布課程摘要（`FR-SUM-01`）。
10. 學生透過聊天助理提問（`FR-CHT-01`~`FR-CHT-03`）。
11. 老師上傳新版課綱時，系統比對差異並通知（`FR-DIF-01`~`FR-DIF-03`、`FR-NTF-04`）。

### 7.2 課綱解析流程

上傳 → 格式檢查（`FR-SYL-01`）→ 文字抽取 → 結構化抽取（`FR-SYL-02`）→ 標註來源與信心（`FR-SYL-03`）→ 狀態設為待確認 → 通知老師（`FR-NTF-01`）→ 老師確認（`FR-SYL-04`）→ 狀態設為已確認。

**失敗路徑**：任一步失敗即停止並保留錯誤原因，不進入下一步；狀態維持可重試（`NFR-REL-01`、`NFR-REL-02`）。

### 7.3 課程與行事曆建立流程

已確認課綱 → 填入課程資訊（`FR-CRS-01`）→ 建立週次章節（`FR-CRS-02`）→ 建立課程事件（`FR-CAL-01`）→ 推送至已授權使用者的 Google 行事曆（`FR-CAL-03`）→ 記錄結果（`FR-CAL-04`）。

**冪等性**：本流程可安全重跑（`NFR-REL-04`）。

### 7.4 通知流程

偵測事件 → 判定對象（僅該課程成員，`FR-NTF-02`）→ 去重檢查 → 交由 Moodle 送出（`D-02`）→ 記錄結果（`DM-OPSTATUS`）。

### 7.5 聊天問答流程

學生提問 → 驗證身分憑證與課程範圍（`FR-CHT-03`）→ 於範圍內檢索課程資料 → 判斷依據是否充分 → 充分則生成含出處的回答（`FR-CHT-01`），不充分則拒答（`FR-CHT-02`）。

### 7.6 課綱更新比對流程

上傳新版 → 解析為新版本 → 與前一版本逐欄位比對（`FR-DIF-01`）→ 標示人工覆寫項目（`FR-DIF-02`）→ 產生說明（`FR-DIF-03`）→ 依嚴重度通知（`FR-NTF-04`）。

## 8. AI 功能規劃

### 8.1 模組分工

| 模組     | 職責                     | 對應需求                              |
| -------- | ------------------------ | ------------------------------------- |
| 文件理解 | 讀取課綱檔案並抽出文字   | `FR-SYL-01`                           |
| 資訊抽取 | 將文字轉為 `DM-SYLLABUS` | `FR-SYL-02`、`FR-SYL-03`              |
| 差異比對 | 版本間逐欄位比對         | `FR-DIF-01`                           |
| 內容生成 | 每週摘要與差異說明       | `FR-SUM-01`、`FR-DIF-03`              |
| 問答助理 | 課程資料檢索與回答       | `FR-CHT-01`、`FR-CHT-02`              |
| 通知判斷 | 決定通知對象與時機       | `FR-NTF-01`、`FR-NTF-02`、`FR-NTF-04` |

### 8.2 使用原則

| 原則                                | 落實需求                                      |
| ----------------------------------- | --------------------------------------------- |
| AI 只協助整理，不得直接改動正式資料 | `FR-SYL-04`（確認關卡）                       |
| 重要資訊須經老師確認                | `FR-SYL-04`、`FR-DIF-02`                      |
| 回答依據課程資料，不憑空猜測        | `FR-CHT-02`、`FR-SYL-02` 的 `unresolved` 規則 |
| 所有 AI 結果保留版本與來源          | `FR-SYL-03`、`NFR-MNT-03`                     |

### 8.3 風險控制

| 風險             | 控制方式                                                       | 對應需求                  |
| ---------------- | -------------------------------------------------------------- | ------------------------- |
| 錯誤摘要         | 摘要僅取用已確認課綱，且保留版本可回溯                         | `FR-SUM-01`、`NFR-MNT-03` |
| 亂寄信           | 單一發送者、發送前去重、通知對象限課程成員                     | `D-02`、`FR-NTF-02`       |
| 提醒錯對象       | 對象一律由 Moodle 選課關係決定，不由 AI 判斷                   | `FR-NTF-02`               |
| 比對漏掉重要差異 | 在結構化資料上做確定性比對而非語言模型比對；新增與刪除皆須偵測 | `FR-DIF-01`               |
| 回答超出權限範圍 | 檢索前先套用課程範圍限制                                       | `FR-CHT-03`               |

### 8.4 分期實作順序

順序依「先消除不確定性」排列，與 §2.4 的版本標記是不同維度。

| 階段     | 內容                                                                      | 目的                                                         |
| -------- | ------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 第一階段 | 以 docker compose 起 Moodle 5.2（document root 指向 `public/`）、資料庫與信件攔截服務；建立 `local_universityai` 骨架，能安裝、出現在管理選單、寫入自有資料表、跑通一個排程任務並發出一則通知 | 驗證 `D-07` 的外掛開發流程、`D-09` 的版本與目錄結構、`D-04` 的寄信前提，不確定性最高而成本最低 |
| 第一‧五階段 | `aiprovider_claude` 的可行性驗證，三項驗收見下方 | 驗證 `D-05` 兩條呼叫路徑都真的成立；這是 `FR-SYL-02` 全部驗收條件的地基 |
| 第二階段 | 每週摘要（`FR-SUM-01`）                                                   | 取得第一條端到端可運作的鏈路，串起排程任務與 AI 子系統 |
| 第三階段 | 課綱解析與確認（`FR-SYL-*`），連帶完成 `FR-CRS-*`、`FR-CAL-*`、`FR-DIF-*` | 投入最多的核心，同步建立測試集與正確率量測                   |
| 第四階段 | 聊天助理（`FR-CHT-*`），含 Moodle 區塊外掛（`D-06`）                      | 依賴前階段的結構化資料；時程不足時採單一課程嵌入的縮小版     |

#### 第一‧五階段的驗收條件

`D-05` 分兩條呼叫路徑的結論，是讀 Moodle 5.2 原始碼得到的；讀原始碼能確定「子系統不支援什麼」，但**不能確定自製供應商實際跑起來會怎樣**。因此本階段是一道實作閘門，未通過不得開始撰寫 `docs/architecture.md` 的 AI 相關章節：

1. **供應商能被子系統識別並呼叫**——`aiprovider_claude` 安裝後出現在站台的 AI 供應商設定中，可建立供應商執行個體、填入金鑰、啟用 `generate_text`，並由 `\core_ai\manager::process_action()` 成功取回一則回應。這驗證生成類路徑，也驗證 `NFR-EXT-03` 的前半段。
2. **抽取介面能取得結構化輸出**——不經子系統，直接由 `aiprovider_claude` 發出一次帶 `DM-SYLLABUS` JSON Schema 的請求，取回的回應通過 PHP 端的 schema 驗證。這驗證 `FR-SYL-02` 的地基。
3. **通用實作的退路真的存在**——以提示詞要求 JSON 的方式重跑第 2 項，量測其 schema 驗證失敗率與重試次數。若這條路完全不可用，`NFR-EXT-03` 的後半段與 `OI-06` 的延後理由同時失效，須立即回頭修改 SRS 而非硬做下去。

三項驗證的實際結果（含失敗的部分）須記入 `docs/architecture.md`，作為後續設計的依據。

## 9. 需求追溯

`D-07` 之後 BDD 由 pytest-bdd 改為 **Behat**——Moodle 內建 Behat 與 PHPUnit 的測試基礎建設，外掛的驗收測試放在各外掛的 `tests/behat/*.feature`，是外掛開發的標準做法。既有的 `tests/features/syllabi.feature` 屬 Python 專案，隨 `OI-05` 一併移除。

feature 檔以需求編號作為 tag，例如：

```gherkin
@local_universityai @FR-SYL-04
Feature: 課綱解析結果的確認
```

追溯表位於 `docs/bdd-guide.md` §11，欄位為：需求編號 → 驗證層級 → 外掛 → 檔案 → 場景或方法名稱 → 架構文件章節。

**驗證層級**

本 SRS 的驗收條件分屬四個層級，各條需求的歸屬見 `docs/bdd-guide.md` §3：

| 層級 | 工具              | 驗什麼                                             |
| ---- | ----------------- | -------------------------------------------------- |
| L1   | PHPUnit           | 純資料轉換、規則判定、不可觀察的內部約束           |
| L2   | Behat             | 使用者可觀察的行為、權限、跨頁面流程               |
| L3   | Python 評測工具鏈 | 語言模型輸出的品質——正確率、拒答適當性、延遲分布   |
| L4   | 人工              | 需要真人判斷或真實外部服務的項目                   |

**追溯規則**

- 每一條版本標記為「必要」的需求，至少對應一個 **L1 或 L2** 的自動化驗證。**L3 與 L4 不得單獨滿足必要需求**——兩者都不在提交流程中執行，若某條必要需求的唯一防線在 L3，日常開發改壞了不會有人發現。
- 使用者可觀察的行為一律另有 L2 場景，即使 L1 已涵蓋其判定邏輯。
- 純資料轉換的邏輯（`FR-DIF-01` 的比對規則、`DM-SYLLABUS` 的約束檢查、`NFR-SEC-06` 的過濾）以 L1 覆蓋即可，不必寫成 Behat 場景。
- 場景中出現的名詞須來自 §1.6 名詞定義。
- 需求變更時，以編號搜尋 tag，同步檢查引用該編號的所有 feature 檔與測試方法。

**`OI-06` 的處理方式（已決定延後）**：第一版以完成功能為優先，不處理合規與費用歸屬。這個延後之所以可接受，是因為 `NFR-EXT-03` 已把供應商切換做成站台設定——所有模型呼叫都經過 Moodle AI 子系統，日後若校方不允許內容送出校外，改用本地或校內模型只需在後台換一個供應商外掛，不必修改任何業務邏輯。換言之，這裡延後的是決策，不是可逆性。
